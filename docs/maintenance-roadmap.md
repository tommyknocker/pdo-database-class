# Карта улучшений PDOdb 2.x

Цель: повысить предсказуемость библиотеки и удобство поддержки существующих приложений. План основан на выборочном аудите и воспроизведениях на SQLite; не считается полным аудитом всех диалектов.

## Принципы совместимости

- Публичные имена и существующие сигнатуры сохраняются, если для исправления не требуется иное. Ошибочные результаты и утечки данных исправляются с отдельной записью в changelog.
- `getOne()` при отсутствии записи продолжает возвращать `false`; документация должна соответствовать этому контракту.
- Старые записи кеша могут перестать использоваться после изменения ключей. Это вызовет временные cache misses, а не изменение данных в базе. Пользовательские ключи и общие кеши необходимо рассмотреть отдельно.
- Изменения, влияющие на результат запросов, проверяются на сочетаниях функций, а не только на отдельных методах.

## 1. Кеш результатов — приоритет P0

**Проблема.** Один и тот же ключ может использоваться для разных форм результата (`get()` и `getOne()`) и для разных баз, использующих общий cache backend.

**План.** Разделить ключи по форме результата и идентичности базы/подключения; версионировать автоматически формируемые ключи. Проверить пользовательские ключи, подключение через переданный PDO, SQLite `:memory:`, read/write splitting, формат выборки и инвалидацию. Не записывать пароль или DSN в открытом виде в ключи.

**Проверка.** Выполнить одинаковый SQL с `get()`, `getOne()` и `getValue()` в разных порядках; использовать общий кеш с двумя базами и убедиться, что результаты изолированы; проверить инвалидирование после записи и существующие тесты кеша.

**Влияние.** Исправляет неверные результаты и потенциальное смешение данных. Старые автоматически созданные записи кеша станут холодными; документировать изменение и настройку namespace там, где идентичность подключения нельзя надёжно определить.

## 2. Scopes и выполнение SELECT — приоритет P0

**Проблема.** Пагинация QueryBuilder не применяет заданные global scopes; `getOne()` не переносит UNION и другие настройки так же, как `get()`.

**План.** Объединить подготовку SELECT в одном пути, применяемом к терминальным операциям, и сохранить маршрутизацию и очистку состояния. Проверить отдельный механизм scopes у ActiveQuery и отключение scopes.

**Проверка.** Две группы tenant: `get`, все три вида пагинации, `getOne`, `getColumn`, `getValue`; UNION, DISTINCT, CTE, JSON и повторные вызовы. Проверить передаваемые параметры.

**Влияние.** Выборки, ранее игнорировавшие условия или операции, начнут учитывать их. Сообщить об этом отдельно: пользователь может наблюдать меньше записей или другой результат.

## 3. Пагинация и ActiveQuery — приоритет P1

**Проблема.** `total` для GROUP BY считает размер первой группы, а не число групп. Делегированный `ActiveQuery::paginate()` возвращает сам ActiveQuery вместо результата.

**План.** Считать строки исходной выборки через подзапрос с учётом DISTINCT/GROUP BY/HAVING и параметров, исключив порядок и ограничения там, где это безопасно для диалекта. Добавить явные методы пагинации ActiveQuery, обеспечив scopes и возвращаемые типы. Проверить поддержку диалектов, включая Oracle и MSSQL.

**Проверка.** Простая и сгруппированная выборка, HAVING и DISTINCT, пустая выборка, несколько страниц, scoped ActiveQuery, три варианта пагинации. Подтвердить SQL и поведение по каждому доступному диалекту.

**Влияние.** `total` и возвращаемый тип станут соответствовать назначению API. Для кода, зависящего от старого ошибочного поведения, нужна заметка об обновлении.

## 4. Диагностика ошибок — приоритет P1

**Проблема.** `DatabaseException::toArray()` может включать значения параметров, в том числе секреты; автоматические и позиционные имена не позволяют надёжно распознать секрет по имени.

**План.** Добавить безопасное представление для журналирования с исключением значений параметров по умолчанию; отдельно определить поведение существующего `toArray()` и обеспечить совместимость. Проверить вложенный контекст, SQL и текст исключения: SQL с литералами и текст драйвера также могут содержать данные и не гарантированно очищаются.

**Проверка.** Именованные, позиционные и автоматически созданные параметры, вложенный контекст и сериализация исключения; явно документировать пределы защиты.

**Влияние.** Если меняется существующий вывод диагностики, отметить это в changelog и предложить явный способ получить подробный контекст для отладки.

## 5. PHP 8.5 и CI — приоритет P1

**Проблема.** CI запускает PHP 8.4; на PHP 8.5 в SQLite и shared тестах возникают deprecations, включая вызовы в production-коде.

**План.** Добавить 8.5 как минимум для SQLite и shared; устранить предупреждения production-кода с сохранением работы на 8.4. Тестовые deprecations устранить там, где это не нарушает совместимость тестов.

**Проверка.** SQLite и shared на 8.4 и 8.5, PHPStan; обозначить реальные ограничения доступной среды.

## 6. Документация и обновление — приоритет P2

**План.** Упростить первый работающий пример в README; исправить контракт отсутствующей строки и заявление о зависимостях; добавить таблицу диалектов и проверяемых версий на основе CI, а также запись в changelog с влиянием на кеш, scopes, пагинацию и диагностику. Не обещать поддержку неподтверждённых сочетаний.

**Проверка.** Запустить первый пример; сверить документацию с composer.json, CI и фактическими результатами тестов.
